# What the literature says about QDA software, coding practice, and analysis — and what it implies for Misket

## 1. Summary

Researchers consistently praise CAQDAS tools (NVivo, ATLAS.ti, MAXQDA, Dedoose) for data management and transparency but criticize steep learning curves, high cost and vendor lock-in, weak team-collaboration and consensus-coding support, and a tendency to "mechanize" analysis by over-emphasizing coding over interpretation [1][2][3]. A large parallel methods literature (Saldaña, Miles & Huberman, MacQueen) describes concrete coding workflows — iterative codebook development, first- and second-cycle coding, splitting/lumping codes, in vivo and flexible coding, memoing, saturation, inter-coder reliability — that a coding tool should make easy to perform and document [26][22][31][34]. Researchers apply a fairly stable set of downstream analysis techniques to coded data — frequency counts, co-occurrence and cross-tab matrices, code-by-case heatmaps, and increasingly joint displays linking codes to quantitative attributes — while repeatedly noting visualization and reporting features lag behind coding features [5][42][46]. Misket already covers a strong share of this ground (hierarchical codebook, merge/move-excerpts, frequency/co-occurrence/heatmap views, descriptors, memos); the clearest open gaps are multi-coder inter-rater reliability, an auditable "living codebook" history, and open interchange (REFI-QDA) to avoid the lock-in the literature complains about most.

## 2. Criticisms of existing tools

**Learning curve and training** — CAQDAS learning is widely described as a "great challenge and obstacle to adoption," with users preferring short, in-context tutorials over marketed "complete" self-learning suites [12][9]. Novice and graduate users report high initial expectations followed by frustration, attributed as much to insufficient methodological training as to software gaps [10][16]. Difficulty mastering the software is itself cited as a reason health researchers under-use CAQDAS at all [2].

**Cost and licensing** — NVivo is priced at roughly $1,249/user as a one-time license with paid upgrades, cited explicitly as a barrier in library/researcher guides [11]. A review of CAQDAS criticism lists "cost and commercialization" as a standing concern alongside a confusing diversity of incompatible packages [14].

**Lock-in, export and open science** — A 2025 systematic review of 28 CAQDAS tools found the field "dominated by proprietary software" with "high costs, vendor lock-in and closed data formats" that "hinder collaboration, data reuse and reproducibility," and found even open-source alternatives under-resourced [3]. The REFI-QDA exchange-format project exists because researchers otherwise cannot move an analyzed project between NVivo/ATLAS.ti/MAXQDA; an experimental transfer study found real but partial gains [49]. Practitioners have called since at least 2016 for a "common exchange format" and closer engagement with open science [50].

**Collaboration** — Even enthusiastic ATLAS.ti users note "a lack of real-time collaboration support" as an explicit limitation [51]. The open-science review found "many tools lack the robust real-time collaboration and detailed audit trails ... necessary for transparency and intersubjective validation" [3].

**Coding UX** — A recurring critique, drawn from Bazeley, is that software-assisted coding can "reduce critical and reflexive reading, mechanizing qualitative analysis" [9]. Reviewers of NVivo/ATLAS.ti/MAXQDA note a "conflation of qualitative data analysis with the coding process" and a risk of "distancing a researcher from his/her data" [7]. A comparison of four QDAS tools coding the same dataset with the same codebook found substantial, unexpected disparities in how each supported basic data organization — tool choice shapes the analysis, not just its speed [13].

**Analysis and visualization** — A content analysis of 763 published studies using ATLAS.ti/NVivo found the "vast majority" of researchers used QDAS only for management and coding, far fewer for visualization or display — the analysis layer is underused partly because it is hard to reach [5]. Design researchers found NVivo "do[es] not fully scaffold the analysis process," strong on data management but weaker for the creative work of building theory, leading some back to paper and colored pens [52]. A review of 21 "CAQDAS dilemmas" notes there is no single right way to use these tools' extensive capabilities, implying the interface itself does not guide users toward good analytic moves [8].

**Transparency and reproducibility** — O'Kane et al. propose explicit "CAQDAS building blocks" and "coder consistency checks" precisely because inductive research done in these tools otherwise "remain[s] shrouded in mystery" [53]. The "Living Codebook" paper argues current tools support intercoder-reliability reporting but not documentation of _how and why_ codes were created, refined and debated over time [24].

**Reliability** — Achieving IRR inside NVivo specifically is reported as methodologically tense even though the statistic (Cohen's kappa) is simple to compute, because the software's coding-unit choices shape the numbers obtained [15]. Guides note that few published studies describe their actual coding/IRR procedures in detail, partly because tools do not make that documentation easy to produce as a by-product of coding [37][38].

## 3. Coding best practices — as concrete workflow statements

- **Codebooks evolve iteratively and need versioning**: teams build a preliminary codebook, pilot it, revise it, and finalize it in cycles [22]. Codebook changes should be tracked over time, not just overwritten.
- **Coders start broad, then split and lump.** Coding is not linear: analysts make codes, reorganize them, and "put patterns together," repeatedly splitting fine codes apart and lumping related ones back together as understanding matures — a normal, expected iteration, not a sign of poor initial coding [31].
- **In vivo, flexible, and abductive coding all need low-friction recoding.** 21st-century interview coding (large samples, team coding, mixed methods) is poorly served by rigid grounded-theory-era assumptions and needs software supporting flexible, revisable coding structures [28]; abductive coding depends on combining codes into "code equations" after the fact [27].
- **First- and second-cycle coding are distinct passes.** Saldaña's Coding Manual frames coding as at least two cycles — open/descriptive/in-vivo first, then pattern/focused/axial second — with memoing threaded throughout [26].
- **"Upcoding" (aggregating child codes into a parent) is a named, deliberate move**, used both to build hierarchical codebooks and to summarize child-code volume at the parent level for reporting [22].
- **Codebooks combine deductive (a priori) and inductive (emergent) codes**, and researchers need to add new codes mid-project without disrupting already-coded data [32].
- **Memo-writing is inseparable from coding**, not a separate downstream step — it should be attachable at the moment of coding, on documents, codes, and individual excerpts [26].
- **Multiple coders need structured consensus processes**, not just a final reliability number: teams report better data quality when codebook development is itself collaborative and disagreements are resolved through discussion, with audit trails of how codes changed [30][29][33].
- **Inter-coder reliability should be computable inside the workflow**, with several accepted statistics (percent agreement, Cohen's kappa, Krippendorff's alpha) depending on design, plus a documented process for resolving disagreements and logging codebook changes [38][37][40][41].
- **Saturation is judged from the coding stream itself** — operational definitions of "code" or "thematic" saturation track when new codes/themes stop appearing across successive units of data, something a tool with full code-application history could surface directly [34][35][36].
- **A "living codebook" documents rationale, not just labels** — definitions, key terms, and a log of why unmatched or renamed codes were resolved a certain way, beyond a static CSV export [24].

## 4. Analysis techniques and displays

- **Matrix and network displays are the core of Miles & Huberman's canonical framework** for going from coded data to conclusions — matrices for exploring, describing, ordering, explaining, predicting [42][44].
- Despite their prominence in methods textbooks, an empirical review of three qualitative journals found matrix/network displays are **used far less often in practice than narrative text**, suggesting friction in producing them, not a lack of interest [43].
- **Co-occurrence treated as a network** reveals structure a simple matrix misses: coding hotline transcripts as a code co-occurrence network (nodes = codes, edges = co-occurrence) surfaced denser code networks in "hopeful" versus "unhopeful" calls that plain frequency counts missed [45].
- **Cross-tabs by participant/document attributes** are a named use case for QDAS (age group, site, wave); Dedoose specifically markets "quantitizing" — turning coded excerpts into countable variables crossed with participant attributes — as a signature feature for mixed-methods evaluators [18][19][4].
- **Code frequency counts** remain the most basic, most commonly reported descriptive output, yet few published studies report _how_ they computed or validated their counts [8].
- **Mixed-methods "joint displays"** (statistics-by-theme tables, side-by-side qual/quant comparisons) are a well-developed methodology for integrating coded qualitative results with quantitative variables; the literature calls for more creative use of charts, maps and images inside them, not just tables [46][47][48].
- Researchers report resorting to **word clouds and ad hoc visualization** for triangulation and bracketing when a tool's built-in analysis views feel insufficient for interpretive work [1].
- **QDAS is disproportionately used for management/coding, not for the visual-display or "predicting" phases** of Miles & Huberman's framework — the content analysis of 763 studies found this explicitly, framing it as unrealized potential rather than researcher preference [5].

## 5. What this implies for Misket

Ranked by how often and how strongly the literature raises the need:

1. **Inter-rater reliability with a disagreement-resolution workflow, not just a kappa number.** Literature: [37][38][40][41][29][15]. → Maps to ROADMAP #21 (Inter-rater reliability, later) and #20 (Multiple coders, later); already correctly scoped, should keep the "disagreement list with resolution" feature since the literature stresses resolution process over the coefficient alone.
2. **A documented, versioned codebook ("living codebook"): who changed a code's name/definition/parent, and when.** Literature: [24][22][33]. → Partially NEW; overlaps ROADMAP #25 (Change log, later) but should extend specifically to per-code definition/rationale history, not just an action log.
3. **REFI-QDA (.qdpx) import/export to counter vendor lock-in and enable interoperability.** Literature: [3][49][50]. → Maps directly to ROADMAP #23 (later); literature frames this as one of the field's most repeated complaints (cost + lock-in + closed formats).
4. **Low-friction split/merge/lump of codes with full undo, and "move excerpts to" to reassign coded material.** Literature: [31][28][27]. → Already **done** in Misket (merge with impact preview, "Move excerpts to…", split/merge excerpts, undo/redo); literature strongly validates keeping and refining this rather than treating it as finished.
5. **Explicit "upcoding" support: view/report a parent code's counts including all descendants, and a fast "promote a code / roll several child codes into one parent" action.** Literature: [22][hierarchical coding search]. → Partially **done** (code frequency table already counts "own and including sub-codes"); recommend adding an explicit codebook action to merge several sibling codes under a new or existing parent in one step.
6. **In-app, task-based onboarding/tutorials rather than a reference manual**, since users prefer contextual, short-form learning over marketed "complete" self-study suites. Literature: [12][9][10]. → NEW; distinct from ROADMAP #9 (keyboard reference overlay, done), which is a lookup tool, not a guided first-run tutorial.
7. **Saturation/emergence tracking: a chart of new-codes-per-document (or per-excerpt) over the course of coding**, letting researchers see when their codebook has stabilized. Literature: [34][35][36]. → Extends ROADMAP #12 (Project overview statistics dashboard, done) rather than a wholly new feature.
8. **A code co-occurrence network view as an alternative to the matrix**, since network layouts revealed structure a matrix alone did not. Literature: [45]. → NEW, complements ROADMAP #4 (Code co-occurrence matrix, done).
9. **A joint-display / mixed-methods export that pairs code frequencies or co-occurrence with descriptor (attribute) values in one table**, beyond filtering matrices by descriptor. Literature: [46][47][48][4]. → Extends ROADMAP #6 (Descriptors, done) and #5 (Code-by-document heatmap, done).
10. **Keep the "no subscription, local-first, one-time cost" positioning explicit in messaging**, since cost/licensing is one of the most frequently named barriers to CAQDAS adoption. Literature: [11][14][3]. → Already Misket's stance (README); recommend surfacing it more directly as a differentiator (e.g., in-app "why Misket" note), not a new engineering feature.
11. **Excerpt-level memos tied into the same audit trail as codebook changes**, so a memo written while recoding is retrievable alongside the definition history from #2. Literature: [26][24]. → Extends existing memos feature (done) + change log (later).
12. **Consensus/dual-coding comparison view**: show two coders' codes on the same document side by side before computing a statistic. Literature: [29][30][33]. → Part of ROADMAP #21/#20 scope; call out explicitly when specifying that feature.
13. **Deductive + inductive code provenance flag** (mark whether a code was defined a priori vs. added during coding), useful for reporting analytic trajectory. Literature: [32][8]. → NEW, small addition to the codebook data model.
14. **Real-time or near-real-time multi-user collaboration** is named as a gap by CAQDAS users, but conflicts with Misket's local-first, single-SQLite-file design. Literature: [3][Paulus ATLAS.ti]. → Flag as an explicit **non-goal for now**; ROADMAP #23 (Project merge, later) is the local-first-compatible alternative and should be described as such when scoping it.
15. **Reporting checklist / "how we used the tool" export** to help authors describe their QDAS use in methods sections, addressing the literature's repeated complaint that studies rarely document software use in detail. Literature: [10][8]. → NEW, low-effort (e.g., an auto-generated "methods appendix" summarizing codebook size, coder count, IRR score, export date).
